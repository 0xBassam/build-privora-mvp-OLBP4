1. Full System Walkthrough

DatabaseMongoDB AtlasMongoDB Cloud

End-to-End Data Flow — Consent Example

  1. Org admin creates a consent request via the dashboard form.
  2. Frontend sends POST /api/consents with title, dataTypes, purpose, legalBasis, retentionPeriod.
  3. Backend validates the JWT token, confirms the user is org_admin, saves to the database.
  4. User logs into their portal, fetches GET /api/consents/requests.
  5. User approves — POST /api/consents/:id/respond with status: "approved".
  6. Backend creates a ConsentResponse record and writes an immutable AuditLog entry.
  7. Org admin dashboard refreshes and shows updated approval rate.

Module Interaction Map

Consent Management
  └── triggers → Data Sharing Gateway (consent required before share)
  └── triggers → Audit Log (every action logged)
  └── triggers → Privacy Notice (notice version recorded)

Data Sharing Gateway
  └── requires → Consent approval
  └── writes   → Audit Log (every transfer logged)
  └── checks   → Purpose Registry (purpose validation)

DSAR Module
  └── references → Consent records
  └── writes     → Audit Log
  └── enforces   → 30-day SLA deadline

Breach Management
  └── writes   → Audit Log
  └── enforces → 72-hour authority notification (PDPL Art. 19)

Compliance Dashboard
  └── reads all modules for aggregated KPIs and score

Key Business Rules

  • Consent cannot be used for data sharing unless status is approved.
  • DSAR SLA is calculated from createdAt and flagged overdue after 30 days.
  • Breach authority deadline is 72 hours from discoveredAt.
  • Consent withdrawal sets status to withdrawn and blocks future data sharing under that consent.
  • All audit log entries are append-only — no update or delete routes exist.
  • Organization data is scoped by organizationId on every query.

Current Limitations

Email Delivery: OTP is generated but email delivery requires an SMTP provider (SendGrid / AWS SES) to be configured. In demo mode, OTP is returned in the API response.
AES-256 Encryption: MongoDB Atlas provides encryption at rest on paid tiers (M10+). There is no explicit application-level field encryption in the current code. See Section 5 for full detail.
File Transfer: Data sharing is metadata-based — no actual file upload or binary transfer system exists yet.
Background Jobs: Expiry checks and SLA calculations happen at query time, not via a scheduler. This is fine at low scale.

Step-by-Step Production Deployment

  1. MongoDB Atlas: Create a cluster, whitelist Railway's IP address, copy the connection string.
  2. Railway: Connect your GitHub repo to Railway. Add all environment variables in the Railway dashboard. Railway auto-deploys on every push to main.
  3. Frontend: Set VITE_API_URL to your Railway backend URL. Run npm run build. Deploy the dist folder to Vercel or Netlify.
  4. CORS: Update the allowed origins in the backend to include your production frontend domain.
  5. Test: Register an org, create a consent request, respond as a user, verify audit log entry.

Data Isolation

Every database query includes an organizationId filter. Org admins can only see their organization's data. Users can only see records targeting their userId. This is enforced at the controller (code) level on every request.

Backup Strategy

Recommended (production): MongoDB Atlas M10+ with continuous backup (point-in-time recovery).

Manual backup command:

mongodump --uri="mongodb+srv://..." --out=./backup-YYYY-MM-DD

Restore command:

mongorestore --uri="mongodb+srv://..." ./backup-YYYY-MM-DD

5. Security Architecture

Authentication Flow

  1. User submits their email address.
  2. Backend generates a 6-digit OTP, stores a hashed version + expiry on the user record, sends OTP to email.
  3. User submits the OTP code.
  4. Backend verifies hash and expiry, issues a JWT access token (15 min) and refresh token (7 days).
  5. Frontend stores the access token in memory and refresh token in localStorage.
  6. Every API call includes: Authorization: Bearer <accessToken>
  7. On 401 response, frontend automatically uses the refresh token to get a new access token.

AES-256 Encryption — Honest Assessment

In Transit: All traffic uses HTTPS (TLS 1.2/1.3). Enforced automatically by Railway and GitHub Pages. ✓
At Rest (Atlas level): MongoDB Atlas M10+ clusters encrypt all data at rest with AES-256 by default. The free tier (M0) does not guarantee this. Use M10+ for production. ✓ (with correct tier)
At Application Level: There is no explicit field-level encryption in the current codebase. Personal data fields are stored in plaintext in MongoDB, protected by access controls and Atlas-level encryption. If enterprise clients require field-level encryption, implement MongoDB CSFLE (Client-Side Field Level Encryption).

API Security Measures in Place

  • Rate limiting on authentication endpoints
  • CORS restricted to the frontend domain
  • Input validation on all POST/PUT routes
  • JWT verification middleware on all protected routes
  • Organization scoping on every data query

7. DevSecOps & CI/CD

Current State

There is no automated CI/CD pipeline in place. Deployment is currently manual:

  • Backend: Push to GitHub → Railway auto-deploys automatically.
  • Frontend: Run npm run build locally → run npx gh-pages -d dist.

Recommended GitHub Actions Pipeline

On push to main branch:
  1. Install dependencies (npm ci)
  2. Run backend tests (npm test) — must all pass
  3. TypeScript check (tsc --noEmit)
  4. Build frontend (npm run build)
  5. Deploy frontend to Vercel via Vercel CLI

8. WAF & Infrastructure Security

Recommended Setup — Cloudflare

Place Cloudflare in front of the entire system. Point your custom domain to Railway through Cloudflare DNS (enable proxy / orange cloud). This provides:

  • DDoS protection
  • Web Application Firewall (blocks SQLi, XSS, path traversal)
  • Rate limiting at the network edge
  • SSL termination
  • Bot detection and challenge pages
  • Real-time traffic analytics

10. Scaling & Future Architecture

Capacity Estimate

ScaleWhat's Needed
0–100 organizationsCurrent setup — no changes required
100–500 organizationsRedis caching, DB indexes, Railway scale-up
500+ / EnterpriseHorizontal scaling, background jobs, API gateway
Government levelAWS/Azure KSA region (data residency), isolated DB per client

Key Additions at Scale

  • Redis caching — cache analytics and consent lists with 60-second TTL.
  • Background job processor — Bull (Redis-backed) for async tasks: OTP emails, SLA checks, retention expiry runs.
  • Database indexing — add compound indexes on (organizationId, createdAt) for all main collections.
  • API Gateway — Kong or AWS API Gateway for auth offloading, analytics, and rate limiting at scale.
  • Data residency — migrate to AWS Riyadh or Azure UAE North for PDPL data localization compliance.
